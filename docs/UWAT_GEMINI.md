# 우왓 사진 분석과 Gemini 연결

현재 방식은 **사진만으로 먼저 판단**하는 방식이다. 설명 입력창·마이크·음성 인식·음성 읽기·운전 중 음성 모드는 제거했다. 기존 지도·공개 민원·기관 관리·GPS와 Gemini 환경변수는 유지한다.

## 사용자 흐름

1. 사진의 외부 AI 처리에 동의한다.
2. 현장 사진을 선택하면 EXIF 제거·크기 조정 후 바로 Gemini로 보낸다. 사용자 설명을 작성하거나 전송 버튼을 누를 필요가 없다.
3. Gemini가 사진에서 관찰한 대상·상태를 판단하고 생활불편·도로·안전재난 분야와 위험 표시·제목·요약·내용을 작성한다. 모호한 경우에만 짧은 선택지로 확인하거나 다른 사진을 요청한다.
4. 결과가 준비되면 알림음을 재생하고 화면 상태·확인 질문을 표시한다.
5. 지도에 저장할 경우 현장 GPS 또는 지도 위치를 별도로 확인하고, 최신 초안에 명시적으로 동의한다. 위치는 사진만으로 추정하지 않는다. 공식 기관 접수는 별도다.

생활불편(living)·도로(road)·안전재난(safety) 메뉴는 탐색 맥락이다. AI가 사진에서 제안한 `suggestedTopic`을 초안과 최종 확인 질문에 표시하고, 확인한 분야로 저장·관리한다. 과거 분야 없는 기록은 도로로 표시한다. Gemini의 `intent=road_report`는 세 분야가 공통으로 사용하는 기존 API 값이다. 사진에서 실제 아차 사고·파손 깊이·법 위반·재난 발생을 단정하지 않는다.

## API

`POST /api/v1/assistant/chat`의 최초 요청은 `photoDataUrl`, `allowAiProcessing:true`, 선택적 `topic`을 보낸다. 사용자 설명인 `message`는 보내지 않는다. 값이 있는 `message`는 `400 TEXT_INPUT_DISABLED`, 사진이 없는 요청은 `400 PHOTO_REQUIRED`다. 확인 답은 활성 질문의 `selection.questionId`·`selection.optionId`로만 전달한다. GPS·지도 좌표는 `location`으로 별도 확인한다.

사진이 바뀌면 이전 사진 판단과 위치를 새 사진에 승계하지 않는다. 이전 입력 방식의 세션은 `409 SESSION_MODE_CHANGED`로 거부하고 새 사진 분석을 요청한다. 기존 방식의 미저장 초안도 공개 저장할 수 없다. 기존에 저장된 기록은 그대로 읽는다. 저장에는 여전히 최신 revision·확인 토큰·명시적 공개 동의가 필요하다.

`GET /api/v1/assistant/status`는 `analysisMode:photo_only`, `audio:notification_only`를 반환한다. 모델명은 서버 `UWAT_MODEL`에서 읽고, 미설정 시 실험한 `gemini-3.5-flash-lite`를 쓴다. 이미 설정된 `UWAT_MODEL`은 그 값을 우선한다. `GEMINI_API_KEY`는 서버에서만 읽는다. 모델 오류 시 일반 규칙 답변으로 AI 판단을 가장하지 않는다.

## 알림음

알림음은 Web Audio의 짧은 oscillator 소리다. 브라우저에서 사진 선택 또는 ‘알림음 준비/확인’ 버튼을 누르면 AudioContext를 준비한다. 마이크 권한이나 음성 서비스가 필요하지 않다. 자동 재생 정책·탭 상태·기기 무음에 따라 소리가 차단될 수 있으므로 화면 상태와 확인 질문을 함께 유지한다. 사진 분석은 알림음 재생 실패와 독립적으로 완료된다.

## 구현 및 검증 범위

RAG는 검수된 공식 FAQ 요약과 내부 기준을 한국어 바이그램 BM25로 검색한다. 검색 문서는 사진에 보이지 않는 현장 사실의 증거로 쓰지 않는다. 모델 답변의 JSON·인용 ID·길이·국내 좌표·확인 동의를 서버에서 검증한다. 사진 자체의 의미적 정확성을 보증하는 것은 아니다.

자동 테스트에서는 사진 없는 요청·설명 입력 거부, 설명 없이 이미지 전달, 선택지 후속 판단, 사진 교체 시 이전 판단·위치 분리, 구 세션 저장 차단, 알림음 준비·재생·차단·종료를 검사한다. 알림음의 실제 청취와 현장 사진 정답률은 실기기·현장 사진으로 별도 확인해야 한다. 모의 테스트와 실제 API 결과는 해당 날짜 검증 기록에서 구분한다.

## 사진 전용 전환 검증 (2026-11-24)

- 최초 사진 선택 후 설명 입력이나 전송 버튼 없이 분석한다. 화면 설명 입력창·마이크·음성 인식·음성 읽기·운전 중 음성 모드를 제거했다. 별도의 Web Audio 알림음을 유지했다.
- AI가 사진으로 suggestedTopic을 제안하고, 최종 질문에서 제안 분야·초안·위치를 확인한 뒤 해당 분야로 저장한다. 저장 후 해당 분야 지도와 상세로 이동한다. 설명 입력은 400 TEXT_INPUT_DISABLED, 사진 없는 분석은 400 PHOTO_REQUIRED로 거부한다. 사진 교체 시 과거 사진의 판단·위치·확인 토큰을 승계하지 않는다.
- 화면·오류 안내·API 소개·현재 사용 문서의 K-ROAD 표기를 정리했다. 기존 환경변수와 파일 경로는 호환성을 위해 유지하며, 기존 연구 모델의 역사적 식별자는 바꾸지 않았다.
- 자동 테스트 43개, TypeScript 검사·production 빌드와 기존 지도·관리자 회귀 검사를 통과했다. 시민 화면 HTTP 200, 사진 패널 입력은 checkbox와 file만 존재하며, 자산 5개 200을 확인했다. 클라이언트 JS/CSS 17개에서 음성 API(SpeechRecognition, speechSynthesis, getUserMedia)와 G-ROAD 문자열은 0건이었다. 알림음 재생·브라우저 차단·종료는 가짜 AudioContext로 검증했다. 실제 기기에서 소리를 청취한 것은 아니다.
- 실제 외부 API를 따로 검사했다. Gemini 기본 연결은 1.69초, 단순한 이미지 응답 형식의 단색 JPEG 판독은 4.94초에 정상 응답했고 보이는 현장이 없다고 판정했다. 전체 우왓 판단 형식 요청에서는 공급자 HTTP 503 UNAVAILABLE과 high demand 응답을 확인했다. 이는 키 누락으로 확인된 문제가 아니며 모델·키 설정을 변경하지 않았다. 전체 사진 분석의 실제 정상 응답과 현장 사진 정확도는 이 실행에서 검증하지 못했다.
- 모델의 unknown 분류는 API에서 null로 정규화하고, 허용 분야·위험 표시·인용·완료 조건은 서버에서 다시 엄격하게 검사한다. [공식 구조화 응답 문서](https://aistudio.google.com/docs/structured-output)를 참고했으며 응답 형식에 맞는 JSON만 저장 단계로 연결한다. 불확실한 사진이나 공급자 오류를 임의 판단으로 대신 저장하지 않는다.
- 실제 API 확인에는 단색 합성 fixture와 임시 저장소를 사용했다. 공개 기록을 만들지 않았고 이 검증에서 만든 세션 파일과 빈 임시 디렉터리만 정리했다. 실제 마이크·GPS·기관 업무 시스템 검증과 구분한다. 새 환경변수·의존성 추가는 없다.

## Gemini 503 대응 (2026-11-24)

- 공급자의 `503 UNAVAILABLE`은 당시 응답의 `high demand`에 따른 일시적 과부하였다. 서버의 기존 350ms 재시도 한 번을 최대 4회 요청, 1·2·4초를 기준으로 한 지수 대기와 약간의 무작위 분산, `Retry-After` 반영으로 바꿨다. 웹 프록시의 100초 제한보다 짧은 전체 85초 예산을 적용한다. `401/403/404`와 잘못된 요청은 반복하지 않는다.
- 모든 시도가 실패하면 기존 `AI_UNAVAILABLE` 또는 `AI_RATE_LIMIT` 오류를 반환한다. 사진 입력은 유지하고 추정 결과나 제보를 자동 저장하지 않는다. 공급자 과부하 자체를 제거하거나 실제 사진 판독의 정확성을 보증하는 변경은 아니다.
- 초기 재시도 수정 후 모의 공급자 응답을 사용한 자동 테스트 49개가 통과했다. 503 두 번 뒤 성공, 계속되는 503과 429, 408 뒤 성공, 인증·모델 오류, 저장 방지 흐름을 확인했다. 당시에는 실제 Gemini 전체 사진 요청을 아직 다시 실행하지 못했다. 이후 실제 호출 결과와 추가 테스트는 아래에 기록한다.

이후 사용자가 제공한 Gemini 키를 프로세스 환경변수로만 전달하여 `POST /v1/assistant/chat`의 실제 사진 분석을 실행했다. 키는 소스·결과·로그에 기록하지 않았다. 사진은 Wikimedia Commons의 [차량 접촉·견인 현장](https://commons.wikimedia.org/wiki/File:Car-accident.jpg), [전면 파손 차량](https://commons.wikimedia.org/wiki/File:Car_Accident.jpg), [포트홀](https://commons.wikimedia.org/wiki/File:Pothole_in_an_asphalt_pavement.jpg), [젖은 도로](https://commons.wikimedia.org/wiki/File:Wet_road.jpg)다. 현장 위치를 알 수 없으므로 GPS를 만들거나 공개 제보를 저장하지 않았다.

사진의 눈에 보이는 핵심 대상은 성공 응답에서 대체로 맞게 식별했지만, 지침 보강 전에는 차량 사진에서 보이지 않는 손상 부위나 현재 사고 위험을 단정하는 표현이 있었다. 지침에 차량 파손과 현재 통행 장애를 구분하도록 추가했고, 재실험에서는 두 차량 사진 모두 통행 영향 확인을 요청했다. 포트홀은 파손으로 식별했고, 젖은 도로를 사고나 포트홀로 확정하지 않았다. 한 번의 502는 실제 Gemini HTTP 200 응답을 앱의 결과 검증이 거부한 사례이며, 원본 모델 출력이 보존되지 않아 원인을 특정하지 못했다.

형식·인용·미완성 응답이 검증에 걸리면 같은 사진으로 최대 한 번 더 모델에 요청하고, 두 결과 모두 기존 서버 검증을 거친다. 전체 85초 시간 제한은 유지한다. 이 보완은 모의 응답 테스트로 검증했으며, 위 마지막 실호출은 첫 응답이 유효했으므로 실제 오류 회복을 입증하지 않는다.

이 수치는 공개 사진 4종의 소규모 탐색 실험이다. 정확도·가동률의 통계적 추정치로 쓰지 않는다. 시간은 파일을 읽고 base64로 준비한 후 서버 핸들러 호출부터 응답까지이며 휴대폰 촬영·압축·네트워크 업로드·GPS 확인·사용자 선택 시간은 포함하지 않는다. 503 과부하와 출력 형식 오류가 재현됐으므로 실사용 준비 완료로 판단하지 않는다. 배포 서버에 `UWAT_MODEL`이 명시돼 있다면 새 기본 모델로 자동 변경되지 않는다.

모델 기본값과 차량 파손 판독 지침 변경 후 자동 테스트 50개, Node 구문 검사, 저장소 인증정보 검사를 통과했다. 자동 테스트는 모의 응답이며 위 표의 실제 API 결과와 구분한다. 웹 빌드·휴대폰 화면·실제 GPS·제보 공개 저장은 이 실험에서 실행하지 않았다.

## 생활불편 세부 분류 및 속도 실험 (2026-11-24)

기존 응답은 `living/road/safety` 분야와 `danger/near_miss/caution` 위험 표시만 구분했다. 실제 생활불편 종류를 알 수 없고, 정상 쓰레기통 사진까지 제보 초안으로 만든 오탐이 실호출에서 확인됐다. 응답에 `issueType`을 추가해 쓰레기 흩어짐·봉투 더미·가로등 고장·시설 파손·포트홀·노면 파손·통행 장애·차량 사고 정황·침수·결빙 의심·낙석 등을 구분하도록 했다. `no_issue`는 관찰되는 불편이 없는 경우이며 저장 토큰을 만들지 않는다. 기존 수동 제보의 `issueType`은 선택 사항으로 남는다. 사진으로 무단투기의 **법적 성립 여부**나 투기자를 판정하지 않는다.

이번 실호출 사진은 [도로변에 흩어진 쓰레기](https://commons.wikimedia.org/wiki/File:Trash_scattered_by_the_road_side.jpg), [정상 쓰레기통](https://commons.wikimedia.org/wiki/File:Recycling_and_Garbage_Bin_in_Municipal_Park.jpg), [보도 위 봉투 더미](https://commons.wikimedia.org/wiki/File:NYC_-_trash_on_sidewalk.jpg)와 앞서 기록한 [포트홀](https://commons.wikimedia.org/wiki/File:Pothole_in_an_asphalt_pavement.jpg), [젖은 도로](https://commons.wikimedia.org/wiki/File:Wet_road.jpg)다. 사람이 사진을 직접 보고 관찰 가능한 정답을 미리 적었다. 봉투 더미의 수거 규정·시각은 사진만으로 알 수 없다. 사진은 평가용이며 강원 현장 사진이나 앱 사용자가 촬영한 사진이 아니다.

| 사진·기대 판정 | 새 분류 지침의 실제 응답 | 첫 호출부터 응답까지 |
| --- | --- | ---: |
| 정상 쓰레기통 → 제보할 문제 없음 | `no_issue/none`, 저장 진행 없음 | 6.30초(503 후 재시도) |
| 도로변에 흩어진 쓰레기 → 생활불편 상태 | `living/trash_scattered`, 위치 확인 전 초안 | 2.68초 |
| 봉투 더미 → 수거 대기 여부 불명 | 첫 호출 503로 실패, 재호출 `living/trash_pile` 확인 질문 | 18.83초 실패 / 2.87초 성공 |
| 같은 봉투 더미 재시험 → 확인 질문 | `living/trash_pile`, 수거 여부 선택 질문 | 17.29초(503·형식 재생성 포함) |
| 위 질문에 “정해진 수거 대기” 선택 | `no_issue/none`, 저장 진행 없음 | 추가 2.19초 |
| 포트홀 → 도로 파손 | 첫 호출 503로 실패, 재호출 `road/pothole` 초안 | 18.57초 실패 / 7.46초 성공 |
| 젖은 도로 → 확인된 사고·파손 없음 | 첫 호출 응답 형식 502, 재호출 `no_issue/none` | 8.77초 실패 / 6.56초 성공 |

서로 다른 사진 5종에 대해 유효 응답에서는 사전 관찰과 일치하는 유형 또는 확인 질문을 얻었다. 다만 실제 최초 분석 요청 9회 중 6회만 정상 응답했고, 2회는 공급자 503, 1회는 형식 검증 502였다. 동일 사진 재시도를 포함한 작은 편의 표본이므로 **정확도 100% 또는 운영 가동률로 해석하면 안 된다.** 성공 요청 6회의 응답 시간 중앙값은 약 6.43초였지만 실패·재시도와 사용자 업로드 시간을 포함한 경험은 더 길 수 있다. 별도 후속 선택 응답은 2.19초였다. 공급자가 정상일 때 약 2~3초 사례가 있었고 503 또는 형식 오류는 훨씬 느리거나 실패했다.

한 후속 응답에서는 사용자의 “정해진 수거 대기” 선택을 사진 관찰 목록에 섞어 썼다. 지침을 보강해 선택 답은 `reason`에만 분리하도록 했지만 이 보강의 실호출 효과는 아직 확인하지 않았다. 포트홀 응답에도 사진에서 실제 깊이를 재지 않았는데 “깊이 파인”이라고 표현한 사례가 있어 서술 정확성 검수가 더 필요하다. 가로등·안전재난·강원 현장 사진은 이번 실호출 표본에 없다.

재현 시 사진당 정답표에 `topic`, `issueType`, `no_issue/확인 질문/초안`, 사진으로 판별 불가한 항목을 먼저 표기하고 원본과 압축본을 함께 보관한다. 최소한 각 세부 유형의 정상·문제·모호한 사례를 확보해 **유형별 정밀도·재현율**, 오탐으로 제보 초안이 만들어진 건수, 미탐 건수, 첫 분석 성공률과 p50/p95 응답 시간을 별도로 보고해야 한다. 같은 사진의 재호출은 독립 사진으로 세지 않는다. 처리 시간은 업로드·압축·GPS·사람 확인까지 추가 측정해야 한다.

이 변경 후 API 자동 검사 42개, 웹 자동 검사 9개, TypeScript 검사를 통과했다. 이 자동 검사는 모의 모델 응답을 사용하며 실제 사진 의미 정확도를 측정하지 않는다.

반복 실험은 `services/api/scripts/photo-eval.mjs`로 실행할 수 있다. 사진은 저장소 밖에 두고 JSON 정답표의 각 행에 `id`, 사진 상대 경로 `file`, 화면 분야 `selectedTopic`, 정답 `expectedIntent`, `expectedTopic`, `expectedIssueType`, `expectedReady`를 적는다. 예: `[{"id":"bin-01","file":"photos/bin-01.jpg","selectedTopic":"living","expectedIntent":"no_issue","expectedTopic":"living","expectedIssueType":"none","expectedReady":false}]`. 서버 환경에 `GEMINI_API_KEY`를 설정한 뒤 `node services/api/scripts/photo-eval.mjs <정답표.json>`을 실행한다. 스크립트는 기존 API 핸들러를 호출하고, 결과 출력에 사진·키·위치를 넣지 않으며 임시 세션을 삭제한다. 행별 결과·유형별 성공 수·성공 응답 시간 p50/p95를 출력한다. 한 장을 여러 번 호출했다면 표에서 동일 사진 ID를 유지하고 별도 반복으로 취급한다. 위치를 주지 않으므로 공개 저장은 실행되지 않는다.

이 평가 스크립트로 위 공개 사진 중 정상 쓰레기통·흩어진 쓰레기·보도 봉투 더미·포트홀 **서로 다른 4장**을 한 번씩 다시 분석했다. 4건 모두 응답했고 사전 정답표의 `intent/topic/issueType/ready` 네 항목과 일치했다. 각 2.666초, 6.279초, 2.738초, 2.830초였으며 성공 응답의 p50은 2.738초, p95는 6.279초였다. 이 4장의 편의 표본을 일반 정확도나 상시 응답 시간으로 일반화하지 않는다. 앞선 503·502 실패 기록과 함께 제시해야 한다.

최종 로컬 확인에서는 웹 TypeScript 검사와 production 빌드도 통과했다. 휴대폰 촬영·업로드·실제 강원 현장·가로등·침수 사진의 성능은 확인하지 않았다. 이 변경은 로컬 작업본에만 있으며 GitHub 원격 배포 상태와 동일하다고 가정하지 않는다.

## 세부 유형별 2차 검증 (2026-11-24)

위 기록 이후 가로등·안전재난을 포함한 구체 유형 12개를 각각 실제 공개 사진으로 시험했다. 독립된 2차 사진 13건 중 12건이 정상 응답했고, 그중 세부 유형 11건, 유형과 초안 준비 여부 모두 10건이 사전 정답표와 일치했다. 정상 응답 시간 p50/p95는 3.287/6.166초였다. 보도 균열의 준비 여부 불일치, 훼손된 가드레일의 낙석 오분류, 침수 사진 형식 오류 1건을 기록하고 지침을 추가했다. 수정 후 다른 사진 3건에서 유형·준비 여부가 일치했지만 표본이 작아 일반 정확도를 뜻하지 않는다. 사진별 결과·출처·아직 필요한 강원 현장 검증은 [사진 세부 유형 평가 기록](PHOTO_CLASSIFICATION_EVAL_20261124.md)에 있다.
